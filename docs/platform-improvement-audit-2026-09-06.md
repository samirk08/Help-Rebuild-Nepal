# Help Rebuild Nepal: website improvement audit

Reviewed 6 September 2026. Recommendation: finish the journey from registration to completed help, with volunteer re-engagement and verified community intake as the next product priorities.

The [live tracker](https://hrn-psi.vercel.app/en/tracker) displayed **191 volunteer registrations**, while the public needs and project pages displayed no verified needs or projects during this review. These are displayed figures, not an independently verified database census. Registration counts also do not establish current availability.

I reviewed the live public HTML, English and Nepali intake, navigation, profiles, networks, needs, relief, projects, partner pages, and the source for authentication, admin operations, exports, uploads, database migrations, and matching/email workflows. This was read-only apart from this report. Browser computer-use permissions prevented rendered desktop/mobile and authenticated interaction testing. Production scheduler configuration, database contents, email delivery, performance, and accessibility compliance remain unverified.

**How the platform currently works**

| Journey | What exists | Main gap |
| --- | --- | --- |
| Volunteers | Registration, optional account claim, profile, matching availability editor | Older registrations lack a straightforward verified return path; profile information is split across old answers and current matching data. |
| Requests | Intake, admin review, public verified board, interest registration | Requesters cannot manage the request through the promised edit/close journey. |
| Matching | Role requirements, eligibility checks, explanations, coordinator invitations, email outbox, accept/decline, confirmation | Operational follow-up, profile refresh, and recovery after changed/expired invitations need completion. |
| Networks | Five skill groups, counts, underlying membership support | Public Join links lead to registration; these are not the nine multidisciplinary missions in your email. |
| Relief | Item needs, offers, pledge verification | Public intake and tracking from pledge through actual delivery are incomplete. |
| Projects | Admin promotion and public cards | Ongoing tasks, progress, completion, and consistent public visibility need work. |
| Coordination | Admin lists, status updates, exports, matching controls | No unified queue of who needs attention, by whom, and by when. |

There is a useful foundation to keep: reviewed publication of needs, English/Nepali content, protected admin access, an explainable matching engine, capacity checks, expiring response links, and an email outbox. The recommendations below build on those pieces.

**Fix first — concrete correctness and access issues**

1. **Verify email ownership before attaching an account.** The account endpoint uses `email_confirm: true`; matching a recently submitted ID and email does not prove access to that mailbox. Add an email code or magic-link verification before linking the registration, with a single-use claim token. Provide the same verified recovery path for older registrations and a password-reset option. This finding does not demonstrate takeover of an already existing account. Evidence: [account creation](/Users/samirkadariya/Developer/HRN/site/app/api/account/create/route.ts:97). Supabase documents that this flag auto-confirms email: [admin createUser](https://supabase.com/docs/reference/javascript/auth-admin-createuser).

2. **Authorize and validate uploads.** The signing endpoint checks that the submission ID exists; the confirmation endpoint checks a path prefix. Neither proves the caller owns that submission. Use an authenticated owner or a short-lived upload capability issued at submission, enforce file/count/storage limits, and verify the actual stored object before recording success. Check file signatures as well as extensions and claimed MIME types. Evidence: [signing](/Users/samirkadariya/Developer/HRN/site/app/api/uploads/sign/route.ts:43), [confirmation](/Users/samirkadariya/Developer/HRN/site/app/api/uploads/confirm/route.ts:37). This follows [OWASP upload guidance](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html).

3. **Validate useful submissions and make retries safe.** Need/volunteer intake mainly checks payload shape and consent, rather than the required identity, contact, skill, date, and quantity fields. Relief branches before that consent check. Introduce a shared server/client schema, sensible length and enum limits, safe handling of malformed bodies, and explicit consent appropriate to each flow. Validate that relief targets are eligible. Add database-backed idempotency: the current last-25-records duplicate check can miss concurrent retries. Add application abuse controls and resource quotas; deployment-level protection was not verified. Evidence: [intake](/Users/samirkadariya/Developer/HRN/site/app/api/submissions/route.ts:180).

4. **Show real states and recover from partial failures.** Missing urgency currently becomes “Immediate”; missing headcount becomes “4” on a real need detail. Filled/completed needs still render an interest action that the API rejects. Failed photo uploads are counted internally but the form ignores that result and redirects to success. Display “Not specified,” actual status, and “Request saved; these photos need retrying.” Separate a failed data load from a true empty state. Evidence: [need detail](/Users/samirkadariya/Developer/HRN/site/app/[lang]/needs/[id]/page.tsx:78), [form submission](/Users/samirkadariya/Developer/HRN/site/components/RequestForm.tsx:104), [upload results](/Users/samirkadariya/Developer/HRN/site/lib/uploads.ts:64).

5. **Make public visibility consistent.** The projects query uses the service role and includes the parent need without checking its publication status. A promoted request can therefore remain represented publicly after rejection/unpublication. Apply one shared publication rule to boards, details, projects, exports intended for the public, and future search indexes. Count confirmed commitments consistently. Evidence: [project reads](/Users/samirkadariya/Developer/HRN/site/lib/community.ts:84).

6. **Limit coordinator access and make exports safe.** Every admin currently has broad access, including generating recovery links for other accounts. Before adding mission leaders or external partners, separate owner, verifier, and mission-coordinator permissions; scope records and exports; restrict account recovery; and audit access changes. Export buttons omit active list filters, and CSV escaping does not neutralize spreadsheet formulas. Preserve filters, paginate exports, and safely encode untrusted cells. Evidence: [admin access links](/Users/samirkadariya/Developer/HRN/site/lib/admin-team.ts:130), [CSV export](/Users/samirkadariya/Developer/HRN/site/app/api/admin/export/route.ts:96). See [OWASP CSV injection guidance](https://owasp.org/www-community/attacks/CSV_Injection).

**Build next — help people actually participate**

7. **Give existing volunteers one “Update my availability” journey.** After verified access, show their saved details and ask only what is missing: confirmed skills, remote/on-site preference, travel area, dates, hours, and contact preferences. Offer optional mission choices when ready. Show “Ready for invitations” with specific remaining actions; the current completeness percentage includes optional historical fields and does not represent matching readiness. Provide clear pause/resume and current commitments. Never turn a database error into “Please register again.” Evidence: [profile loading and completeness](/Users/samirkadariya/Developer/HRN/site/lib/volunteer-profile.ts:73).

8. **Turn the nine missions into real, multidisciplinary teams.** Let people select one or two missions without requiring an order. Keep them eligible for wider opportunities unless they explicitly choose mission-only invitations. Each mission needs a lead, a short purpose, skills needed, one concrete next task, and a meeting/update link. Separate “registered expertise” from “opted-in mission members”; current network counts include inferred membership. Wire Join/Leave to actual membership instead of registration. Collect choices across all missions, then activate one or two teams with a clear lead and task first. This is consistent with IFRC's emphasis on locally relevant roles, volunteer participation, and continuing coordination: [volunteer management guidance](https://solutions.ifrc.org/node/73). Evidence: [current Join links](/Users/samirkadariya/Developer/HRN/site/app/[lang]/networks/page.tsx:49).

9. **Shorten intake and add assisted community requests.** The volunteer form has seven sections and the need form nine; only consent is enforced with an HTML `required` attribute. Start with the task/problem, location or remote option, contact, and urgency; gather detailed role requirements during verification. Separate phone and email, permit a phone-only assisted route, and use suitable input types, error messages, and a review step. A coordinator should be able to record a phone/WhatsApp request with its source and consent. Pilot intake with municipalities and community organizations so actual needs reach the platform. Simplifying questions before adding progress decoration follows [GOV.UK form guidance](https://design-system.service.gov.uk/patterns/question-pages/). Evidence: [form](/Users/samirkadariya/Developer/HRN/site/components/RequestForm.tsx:74), [field rendering](/Users/samirkadariya/Developer/HRN/site/components/FormField.tsx:76).

10. **Give requesters a secure management page.** The form promises they can update or close requests, but that workflow is absent. A verified management link should show review status, assigned coordinator, questions awaiting an answer, agreed volunteers, and actions to update, close, or reopen. Important edits should trigger re-review and refresh affected invitations. The requester should explicitly confirm that the proposed connection is useful and later that help happened. Keep phone-assisted support available for people who cannot use email.

11. **Make Situation Room a daily action queue.** Organize by action and urgency: new needs awaiting verification, unanswered clarifications, missing volunteer details, accepted invitations awaiting coordination, overdue work, and unresolved feedback. Each item needs an owner, next action, due date, and activity history. Add quick search by name/contact, skill and mission filters, and pagination. Replace the public partner page's static dashboard with a useful explanation and a real sign-in/contact route; show operational figures only in the appropriate authenticated workspace. Evidence: [partner page](/Users/samirkadariya/Developer/HRN/site/app/[lang]/partners/page.tsx:6).

12. **Finish matching follow-up before increasing automation.** Keep the current explicit eligibility checks and explanations. Missing evidence should request clarification, not silently become a match or rejection. Add reminders to refresh stale availability, a coordinator alert when someone accepts, delivery-failure follow-up, and a visible worker heartbeat/oldest queued email. There is a worker endpoint, but I could not verify a production schedule. Introduce versioned invitation attempts: the current “ever approached” rule also blocks cancelled or expired invitations for the same role, including after role changes. Preserve explicit declines unless the volunteer opts back in. Align public headcounts with role slots, and extend structured language/resource requirements only when a role needs them. Evidence: [engine](/Users/samirkadariya/Developer/HRN/site/lib/matching/engine.ts:48), [worker](/Users/samirkadariya/Developer/HRN/site/lib/matching/worker.ts).

13. **Track supplies through receipt.** Provide an explicit “I need supplies” intake that creates an item need. Use quantities and stages for requested, pledged, reserved, dispatched, and received, including partial deliveries and remaining demand. Today verified pledges contribute to totals, but generic status changes do not reliably represent delivered assistance. Add the delivery contact, arrangement, and recipient confirmation. Prevent closed or fully allocated needs from collecting misleading new commitments. Evidence: [relief data](/Users/samirkadariya/Developer/HRN/site/lib/relief-data.ts), [relief intake](/Users/samirkadariya/Developer/HRN/site/app/api/submissions/route.ts).

14. **Make projects show work and outcomes.** Give each project a real detail page, lead, tasks, milestones, latest update, output links, and requester-confirmed completion. Prevent duplicate promotion of the same need. Keep sensitive rosters and contact details private; publish useful redacted progress. A mission can prepare reusable material before a need arrives, but field work should have a locally verified brief and accountable lead. Evidence: [project read model](/Users/samirkadariya/Developer/HRN/site/lib/community.ts:53).

**Improve reach, trust, and reliability alongside those journeys**

15. **Make mobile and Nepali journeys complete.** Prioritize “Get help” and “Offer help” in navigation; use readable mobile request cards with visible field labels. Translate form introductions, matching forms, emails, errors, and response pages consistently. Respect the recipient's language instead of always linking to English. Test keyboard operation, error focus, screen readers, text zoom, and narrow screens in both languages. Source inspection found risks; this is not a measured accessibility failure report. Use [WCAG 2.2](https://www.w3.org/TR/WCAG22/) as the acceptance standard.

16. **Support unreliable connections.** Add deliberate draft saving, compressed photo uploads, per-file retry, and clear saved/queued/sent states. Keep temporary local data optional on shared devices and give it an expiry/deletion path. Pilot an assisted offline collection tool before building full offline synchronization. [KoboToolbox's documented forms](https://support.kobotoolbox.org/data_through_webforms.html) provide a relevant example of cached forms, drafts, and queued submissions; their behavior is a reference, not an existing HRN capability.

17. **Help users find and share actionable needs.** Default to open, urgent requests rather than alphabetical district order. Add clear task titles, remote/on-site and date filters, and an explanation of why a request fits someone's profile. Correct per-page canonical URLs: live subpages currently inherit the locale homepage canonical. Add localized sharing previews and a sitemap of eligible public pages. Consider linking verified requests to relevant [BIPAD risk information](https://bipadportal.gov.np/risk-info/) after checking suitability and data freshness; precise household locations should not become public by default. Evidence: [board](/Users/samirkadariya/Developer/HRN/site/components/NeedsBoard.tsx), [locale layout](/Users/samirkadariya/Developer/HRN/site/app/[lang]/layout.tsx).

18. **Make trust and feedback visible.** Explain who verifies requests, what verification means, how to contact HRN, and realistic response expectations. Provide a way to report inaccurate information, an unsafe interaction, or help that never arrived, with an assigned follow-up owner. Add readable privacy, retention, contact-sharing, and withdrawal choices; current “withdrawable at any time” copy needs an actionable route. Use role-appropriate credential and supervision checks for specialist work. Review sensitivity before publishing either individual or aggregate data, following [OCHA responsible-sharing guidance](https://centre.humdata.org/guidance-note-responsible-approaches-to-data-sharing/).

19. **Measure useful help, with honest counts.** Replace hardcoded logistics zeroes with “Not yet collected.” Distinguish registrations, recently available volunteers, opted-in mission members, confirmed assignments, and completed work. Track time to acknowledge a need, time to a suitable response, acceptance rate, unmet needs, delivery completion, and requester feedback. Show when data was updated and when a load fails. These measures will reveal whether future ranking changes help. Evidence: [metrics](/Users/samirkadariya/Developer/HRN/site/lib/metrics.ts:14).

20. **Make production failures visible and releases repeatable.** Add CI for existing tests/type checks/build plus meaningful integration coverage for claim ownership, upload authorization, duplicate retries, invitation lifecycle, and capacity contention against PostgreSQL. Monitor queue age, retries, webhook failures, and unavailable public reads. Verify migration state, staging separation, and backup restoration. The diagnostics page currently writes/deletes a probe during a GET and omits newer migrations; use explicit safe probes. Update documentation to match the implemented platform. Measure real mobile performance before deciding what to optimize. Evidence: [diagnostics](/Users/samirkadariya/Developer/HRN/site/app/admin/(dashboard)/diagnostics/page.tsx), [Web Vitals guidance](https://web.dev/articles/vitals).

**Recommended implementation order**

| Step | Deliverable | How to know it works |
| --- | --- | --- |
| 1 | Ownership/upload fixes, validated retry-safe intake, accurate public states, publication rules | Unauthorized claims/uploads fail; retries create one record; failed uploads can recover; unpublished requests stay unpublished everywhere. |
| 2 | Verified return journey, current availability, mission choices and real membership | An existing volunteer can return, correct details, choose missions, pause/resume, and become eligible without duplicate registration. |
| 3 | Assisted intake, requester management, Situation Room, matching follow-up | A real pilot request can be verified, offered, accepted or declined, coordinated, and closed with requester feedback. |
| 4 | Supply receipt tracking, project progress, scoped partner access | Coordinators can distinguish promised help from received help and resolve overdue work. |
| 5 | Broader mobile/localization refinement, offline pilot, discovery and impact reporting | Field testing shows people can complete the journeys; reports reflect current activity and outcomes. |

Apply essential mobile usability, translation, authorization, and monitoring within each step; the final step extends coverage. Start with one complete pilot request and one or two mission teams, record where coordination stalls, and use that evidence to choose subsequent enhancements. The main constraint today appears to be completing and operating these journeys, rather than the matching formula itself.
