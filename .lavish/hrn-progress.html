Phase 1 — what was actually unsafe

Each of these looked like a safeguard and was not.

Anyone holding a submission id could take your account

Was

An id plus a matching email created an account marked email_confirm: true — a mailbox verified that nobody had proved control of. Those ids travel in URLs, browser history and forwarded links.

Now

Nothing is linked until a one-time code sent to that mailbox comes back. The 24-hour window is gone, so someone returning to an old registration can claim it instead of registering twice.

An HTML file renamed photo.png was stored and linked

Was

Uploads were authorised by “does a row with this id exist?”, which is not authorisation. The file type came from the extension — a value the caller chooses.

Now

A session or a signed ticket is required, and the first 32 bytes of the stored object decide its real type. Quotas count what the submission already holds.

Public pages invented the answers people had not given

Was

A missing urgency rendered as “Immediate”. A missing headcount rendered as 4. A filled request still showed “Verified” and still collected offers of help.

Now

Unanswered says “Not specified”. One shared publication rule across board, detail, counts and projects. A failed read says it failed instead of showing an encouraging zero.

Phase 2 — mission teams and a real workspace

Nine missions, capped at two

Housing · Health camps · Mental health · Flood resilience · WASH · Operations & IT · Story & advocacy · Situation Room · Temporary shelter.

The two-mission cap is a database trigger that locks the row before counting, not a form check — a browser limit holds until someone opens two tabs.

Purpose, lead and current task are seeded blank, as you asked. Each says “not set yet” rather than inventing work that does not exist.

Choosing a mission does not narrow your invitations

Interest is not a filter. Only the explicit “only invite me to needs within my missions” switch changes scope — off by default, reversible in one click, and it does not remove you from the missions.

Missions are deliberately separate from skill networks. A network says you are an engineer; a mission says you want to work on housing. Merging them would let your profession silently enrol you in a team.

“Ready for invitations”

Lists only what is missing, and says who fixes each item — you, or a coordinator. Not a percentage: there is no meaningful “62% ready”, and a score invites gaming the number instead of filling the gap.

A test asserts this agrees with the matching engine. A page that calls you ready while every role comes back “needs clarification” is worse than no page.

Open invitations and commitments

What is waiting on you, and what you have already agreed to.

Committed hours use peak overlap, not the sum. Two jobs in different months do not add up — saying they did would tell someone they are full when they are free, and quietly stop invitations they could have accepted.

Four bugs found along the way

Three of these pre-dated this work. The interesting thing is what they have in common.

“Join network” always sent you back to the registration form

You reported this one. The button, the API route and the permission check all existed and were correct — nothing referenced them. Every card rendered a hardcoded link to the form, so one-click join never existed for anyone.

Found by: you, using the site.

Mission fields the engine read but nothing could write

The matching engine already used mission_ids and mission_only. No table held missions and no form wrote those columns. Same shape as the join bug, one layer down.

Found by: reading the engine before building on it.

Diagnostics told you your forms were broken when they were not

My bug. The ledger looked for a table called admin_allowlist; it is called admin_users. The page contradicted itself on one screen, and a missing optional feature was reported as “public forms are likely returning errors”.

Found by: you, screenshotting the page.

A database blip told registered people to register again

A failed read returned “no registration”, which renders as “You have not registered yet” with a link to the form. Filling it in produces a second row for the same person — the exact duplicate the claim flow exists to prevent.

Found by: the plan naming it as a rule, then checking whether the code obeyed.

What they had in common

Typecheck passed. Every test passed. The build passed. Working code that nobody calls is still valid code, so none of those could see it — the defect was in the wiring, and nothing checked wiring.

There is now a test that fails when a component talks to the backend and no page renders it. I verified it by reverting the fix and watching it fail, because a regression test that only passes against the fix is worth nothing.

Something worth knowing about the automated PRs

Seven arrived from a bot while this was in progress. Four were taken, three declined.

All seven showed green checks — and the checks never ran your tests. They were Vercel builds only. That is how a test file that does not compile and a branch whose build fails were both reported as passing. There is now a real CI workflow running typecheck, tests and build on every PR.

The one I most wanted to decline proposed a recursion guard that would have made two different oversized payloads produce the same idempotency key — silently discarding the second person's registration as a duplicate. Losing a registration is worse than the crash it prevented.

What is deliberately not done

Volunteer contact-sharing controls

Contact details are already exchanged only at both-party confirmation, which is the coordination step the plan requires — so the privacy guarantee holds today. A volunteer-level opt-out is new policy plus a migration, and belongs with Phase 4.

Single-need reads during an outage

One need page still 404s if the database is unreachable, rather than saying “unavailable”. The list surfaces the plan named are covered; this one is honest about being a gap.

Distributed rate limiting

The limiter is in-process per instance: real against one script in a loop, useless against a distributed flood. The size limits, option allowlist, upload quotas and idempotency key all hold regardless.

Phase 3, when you want it

A three-step need intake

The request form is currently nine sections. Phase 3 cuts it to need, contact, review — with detailed role requirements moved into the verification step where a coordinator fills them in, rather than demanded from someone in a crisis.

Plus a phone/WhatsApp-assisted path that records who helped and that consent was given.

A workspace for the person who asked for help

Right now a requester submits and hears nothing. Phase 3 gives them a verified link to see status, answer questions, update the request, confirm or decline a proposed volunteer, and say whether the support actually met the need.

With version numbers, so an edit cannot silently overwrite a newer coordinator update.
